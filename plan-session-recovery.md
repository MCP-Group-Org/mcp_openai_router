# План: Автоматическое восстановление сессии think-tool при рестарте

## Описание задачи

После рестарта контейнера `mcp_think_tool` сервис `mcp_openai_router` продолжает использовать устаревший `mcp-session-id`, что приводит к ошибкам `HTTP 400 Bad Request`. Клиент `ThinkToolClient` кэширует `_session_id` и `_initialized` в памяти и не выполняет повторный handshake автоматически.

**Цель:** Реализовать механизм автоматического обнаружения устаревшей сессии и автоматического пересоздания соединения при получении 400 ошибки от FastMCP.

## Анализ кода

### Корневые причины проблемы

1. **Глобальный singleton клиента** (`app/core/config.py:40`):
   - `THINK_TOOL_CLIENT` создается один раз при старте приложения
   - Живет до перезапуска роутера

2. **Кэширование состояния сессии** (`app/think_client.py:92-93`):
   - `_session_id` — кэшируется и не пересоздается автоматически
   - `_initialized = False` — блокирует повторный handshake

3. **Недостаточная обработка ошибок** (`app/think_client.py:276-281`):
   - При 400 ошибке выбрасывается RuntimeError
   - Внутреннее состояние (`_session_id`, `_initialized`) не сбрасывается
   - Клиент остается в "сломанном" состоянии

4. **Отсутствие механизма восстановления**:
   - Метод `_ensure_initialized():179` пропускает инициализацию если `_initialized=True`
   - Нет автоматического обнаружения устаревшей сессии
   - Нет retry-логики после получения 400 с сообщением о невалидной сессии

### Последствия

- После рестарта think-сервиса все запросы получают 400 Bad Request
- Требуется ручной рестарт роутера для восстановления работы
- Нет автоматического самовосстановления (self-healing)

## Подход к решению

Реализовать паттерн **"автоматическое восстановление при сбое"** (automatic recovery):

1. **Обнаружение проблемы**: При получении HTTP 400 с текстом "Invalid or expired session ID" или "No valid session ID provided"
2. **Сброс состояния**: Очистка `_session_id` и `_initialized`
3. **Повторная попытка**: Автоматический retry с новым handshake (ограничение: max 1 retry)
4. **Логирование**: Расширенное логирование для диагностики

## Альтернативные подходы

### ✅ Вариант A: Локальный retry в `capture_thought()` (текущий план)

**Плюсы:**

- Минимальные изменения кода
- Целенаправленное решение конкретной проблемы
- Низкий риск побочных эффектов
- Легко тестировать и отлаживать

**Минусы:**

- Retry только для `capture_thought()` (но это единственный публичный метод клиента)

### Вариант B: Централизованный retry внутри `_post()`

**Плюсы:**

- Единое место обработки retry
- Автоматически работает для всех внутренних вызовов

**Минусы:**

- Усложняет логику `_post()`
- Сложнее контролировать поведение для разных типов запросов
- Может привести к неожиданным retry во время handshake

### Вариант C: Периодический health-check сессии

**Плюсы:**

- Проактивное обнаружение проблем до реального запроса
- Меньше ошибок в production

**Минусы:**

- Дополнительная нагрузка на think-сервис
- Требует фоновый поток/задачу (asyncio)
- Избыточно для текущей проблемы
- Усложняет архитектуру

**Решение:** Выбран **Вариант A** как наиболее простой и эффективный для решения текущей проблемы.

## Риски и ограничения

1. **Производительность**:
   - Retry добавляет задержку (~timeout think-сервиса + время handshake) при первом запросе после рестарта
   - Оценка: 2-5 секунд дополнительного времени для первого запроса

2. **Бесконечный цикл**:
   - Риск: если think-сервис постоянно возвращает 400
   - Митигация: строгое ограничение max 1 retry на вызов

3. **Race condition**:
   - Если несколько запросов одновременно обнаруживают устаревшую сессию
   - Возможны параллельные handshake (создание нескольких sessionId)
   - Не критично: последний успешный перезапишет `_session_id`, все будут работать

4. **Зависимость от текста ошибки**:
   - Решение опирается на текст ошибки от FastMCP
   - Риск: текст может измениться в будущих версиях FastMCP
   - Митигация: использовать несколько паттернов для обнаружения

5. **Ограничение retry**:
   - Только 1 попытка восстановления
   - Если think-сервис нестабилен, может потребоваться повторный запрос от клиента
   - Приемлемо для текущего сценария (разовый рестарт)

## Корректировки на основе peer-review (Codex)

### Исправленные критические ошибки

#### ❌ Ошибка 1: Слишком общий маркер "Bad Request"

**Проблема:** Изначально план предлагал проверять просто "Bad Request", что могло вызвать ложные срабатывания.

**Исправление (Шаг 2):** Проверять только специфичные маркеры:

- ✅ "No valid session ID"
- ✅ "Invalid or expired session"
- ✅ "expired session ID"
- ❌ НЕ "Bad Request" — слишком общее!

**Обоснование:** FastMCP может вернуть 400 по разным причинам (невалидный JSON, неизвестный метод и т.д.). Только ошибки, связанные с сессией, должны вызывать автоматический retry.

#### ❌ Ошибка 2: Неверное ожидание количества вызовов _post

**Проблема:** Тест проверял "количество вызовов = 2", но после retry происходит полный handshake.

**Исправление (Шаг 5, тест 1):**

- Вместо подсчета вызовов проверять изменение `session_id` (старый ≠ новый)
- Или проверять успешное завершение `capture_thought()` с `ok=True`

**Обоснование:** После `_reset_session()` выполняется:

1. `_ensure_session()` → POST ping
2. `_send_initialize()` → POST initialize
3. `_send_initialized_notification()` → POST notification
4. Повторный вызов tools/call

Итого: минимум 5 вызовов, а не 2.

#### ❌ Ошибка 3: Проверка _session_id = None после retry

**Проблема:** Тест пытался проверить `_session_id = None` после завершения `capture_thought()`.

**Исправление (Шаг 5, тест 3):**

- Использовать mock/spy для отслеживания вызова `_reset_session()`
- Проверять, что `_session_id` после завершения **НЕ None** (новая сессия уже создана)

**Обоснование:** Последовательность retry:

```code
capture_thought()
  → 400 error
  → _reset_session()      # _session_id = None
  → _ensure_initialized()  # _session_id = "new-xyz"  ← handshake!
  → return success
# _session_id уже заполнен!
```
