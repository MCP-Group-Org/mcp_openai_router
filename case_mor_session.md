# Проблема сессии `mcp_openai_router` после рестарта think-сервиса

## Описание

После пересборки/перезапуска контейнера `mcp_think_tool` сервис `mcp_openai_router` продолжает использовать старый `mcp-session-id`. Клиент `ThinkToolClient` (поля `_session_id`, `_initialized`) кэширует значения в памяти процесса и больше не выполняет handshake, пока не будет перезапущен сам роутер или не сброшены флаги. В результате каждый новый `POST /mcp` отправляется с устаревшим заголовком `mcp-session-id`, FastMCP отвергает запрос на уровне транспортного слоя и возвращает `HTTP 400 Bad Request`. Это проявляется в логах роутера как:

- `Received tool calls: …`
- `HTTP Request: POST http://mcp-think:8080/mcp "HTTP/1.1 400 Bad Request"`
- `think-tool вернул 400: None`

При этом в логах think-сервиса отсутствуют записи `think tool invoked`, что подтверждает сбой до вызова инструмента.

## Подход к решению

- Зафиксировать, что после рестарта think-сервиса необходимо либо перезапускать `mcp_openai_router`, либо научить `ThinkToolClient` автоматически сбрасывать `_session_id` и `_initialized` при получении 400/404 от FastMCP.
- В рамках диагностики расширить логирование `_post` (уже рекомендовано в `diagnostic_router.md`), чтобы явно видеть `sessionId`, статус и тело ответа.
- Рассмотреть дополнение `_ensure_session` повторным handshake по требованию (например, при конкретных ошибках `Invalid or expired session ID`).
- Отмечено, что FastMCP уже возвращает текст `"Bad Request: No valid session ID provided"`, но клиент `_post` пытается трактовать его как JSON и теряет сообщение. Исправление: логировать `response.text`, сбрасывать сессию при обнаружении этой строки и/или поменять think-сервер, чтобы он возвращал структурированный JSON-RPC-ответ (тогда клиент сможет однозначно разобрать причину).
